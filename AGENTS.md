## Product Boundaries

Critical rule:

```text
The files under /data belong to the user. Mangayomi reads them; it only
changes them through the two-step deletion flow.
```

- Scanning, cover generation, and page serving must never write to `/data`.
  Derived state (database, covers) belongs in `/config`.
- The only code path that removes user files is `internal/deletion`. Do not
  add another. Any new destructive action must go through a preview that lists
  the exact paths, a short-lived single-use token, and a confirmation that
  deletes only what the preview listed.
- Every path taken from the database or a request must be re-validated against
  the data directory and its library root before it is opened or removed. The
  library root itself is never deletable.
- A work is identified by `(library, relative path)`. Author and series are
  derived metadata from the folder pattern; they are not identities and may
  change when the pattern changes. Do not key user state on them.
- A folder that directly contains images is a work; the scanner does not
  descend into it and its name is always the title. Keep that rule when
  changing the walker.
- An unreadable library root or sub-folder must never be interpreted as
  "all works were deleted". Scans that cannot see a directory keep its index.

## Code Organization

Dependencies point downward:

```text
cmd -> internal/api -> feature packages (scanner, deletion, auth) -> store, media -> natural, config
```

- `internal/api` translates HTTP to package calls. Keep domain logic,
  persistence, and filesystem effects in their packages so they stay testable
  without HTTP.
- `internal/store` owns SQL. Other packages do not build queries.
- On the frontend, pages compose components; components do not import pages.
  Shared helpers live in `web/src/lib` and hooks in `web/src/hooks`.
- `web/src/components/ui` is generated by the shadcn CLI. Prefer adding a
  component with the CLI over hand-writing a primitive, and avoid editing
  generated files unless a fix is required.

## UI and Test Contracts

- Follow `docs/development/design.md`. Use semantic theme tokens; the reader
  is the only surface with a fixed dark background.
- Every user-visible string goes through i18next. Add keys to
  `web/src/i18n/locales/en.json`; English is the only required locale.
- API responses must serialize empty lists as `[]`, never `null`; the frontend
  relies on it.
- Tests should protect a concrete behavior, contract, security boundary, or
  prior regression. Choose the lowest sufficient layer. Follow
  [Synthetic Fixture Data](docs/development/testing.md#synthetic-fixture-data):
  fixtures use generic names such as `Author A` and `Series One`, never real
  titles, authors, or personal paths.

## Validation Commands

The `Makefile` is the canonical entry point for repository validation. Prefer
its targets over reconstructing commands by hand so local checks and CI run the
same commands.

- Use the smallest sufficient target: `make docs` for documentation,
  `make ci-style` for formatting, lint, types, and docs, `make ci-backend` for
  backend behavior, and `make ci-frontend` for frontend dependencies and build.
- Use `make smoke` for Docker, entrypoint, or runtime changes. It builds the
  image and exercises setup, scanning, page serving, and deletion against
  disposable mounts.
- `make ci-local` runs everything CI runs.
- Before every commit, run `make sensitive-check` and review every finding.
  Do not silence it with source comments; add a reviewed entry with a reason to
  `scripts/sensitive-allowlist.json` only for data that is genuinely public.

## Release and Handoff

- `VERSION` is the single source of the application version. The Makefile and
  Dockerfile inject it into the binary. Do not hard-code a version elsewhere.
- The schema lives in the `migrations` list in `internal/store/store.go`.
  Released entries are immutable; append a new entry for every schema change
  and never edit or reorder an existing one. Existing databases migrate on
  startup.
- Record user-visible changes in `docs/history/unreleased.md`.
- Before handoff, run validation proportional to the change and
  `make sensitive-check`.

Public tracked code and docs must use generic examples: reserved domains,
`/path/to/manga`-style paths, and synthetic names. Never commit databases,
media, covers, logs, `.env` files, personal paths, or e-mail addresses. Ignore
rules are not a secrecy boundary.
